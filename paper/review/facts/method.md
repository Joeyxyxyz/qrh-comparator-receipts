## 1. What Comparator is and what it compares

- **M1.1 Identity.** Comparator is the Lean FRO's proof judge, taking a statement file and a proof. `KIT/docs/PROTOCOL.md` lines 24 to 26: "Comparator is the Lean FRO's judge for exactly this situation: someone hands you a statement you can read and a proof you cannot. It needs two modules. The *challenge* states the theorem with the proof left out. The *solution* states it again with a proof." Sources named in `KIT/NOTICE`: "Comparator        https://github.com/leanprover/comparator        Apache-2.0   Lean FRO" and "lean4export       https://github.com/leanprover/lean4export       Apache-2.0   Lean FRO".
- **M1.2 The five steps.** `KIT/docs/PROTOCOL.md` lines 30 to 38: "1. builds the challenge inside a sandbox; 2. exports the challenge statement and every definition it refers to; 3. builds the solution inside the sandbox (the long step: 2,943 files); 4. exports the solution's theorem with everything it depends on, then checks that the two statements are identical, definition by definition, and that the proof uses no axiom outside the permitted list (`propext`, `Quot.sound`, `Classical.choice`: Lean's three standard ones); 5. replays the exported proof, all of it, through the Lean kernel." and "It prints `Your solution is okay!` and exits 0 only if all of that succeeds." (The quote joins the five numbered lines of the source with semicolons.)
- **M1.3 The configuration file.** A JSON file with the keys `challenge_module`, `solution_module`, `theorem_names`, `definition_names`, `permitted_axioms`, `enable_nanoda`. `GEN` lines 138 to 139: `cfg = {"challenge_module": CHALLENGE_MODULE, "solution_module": SOLUTION_MODULE, "theorem_names": all_claimed, "definition_names": [], "permitted_axioms": ["propext", "Quot.sound", "Classical.choice"], "enable_nanoda": True}`. The kit's control configurations have no `definition_names` key (`KIT/controls/pass/config.json`: `"theorem_names": ["qrh_control"]`, `"permitted_axioms": ["propext", "Quot.sound", "Classical.choice"]`, `"enable_nanoda": false`).
- **M1.4 `theorem_names`.** The names whose statements must agree between challenge and solution and whose proofs are checked. Evidence by behaviour, `KIT/controls/wrong_statement/expected.json`: `"must_contain": "theorem statement do not match: 'qrh_control'", "why": "a proof of a different statement under the same name must be rejected"`.
- **M1.5 `definition_names` (holes) versus full comparison.** A definition listed there is a hole: only name, type and universe levels are compared. With the list empty, definitions are compared by name, type and body. `REPO/sources/qrh-mnf-addon-v2/README.md` lines 36 to 38: "In v2 the config's `definition_names` is empty, so Comparator compares every definition by name, type and body (in v1 the 17 definitions were listed as holes, which Comparator compares by name, type and universe levels only)." Counts in the configs: run 3 `definition_names` has 17 entries, runs 4 and 5 have 0 (`REPO/sources/qrh-mnf-addon*/MNFChallenges/RH.json`); runs 6 to 11 write `"definition_names": []` (`GEN` line 139; `REPO/sources/qrh-zeta23-addon/README.md` line 55: "no definition holes, NanoDa enabled").
- **M1.6 Consequence recorded for run 3.** `REPO/DEPOSIT_MAP.md` lines 143 to 147: "The v1 run (2026-10-28, ACCEPTED) compared the 40 statements but listed the 17 definitions as holes, which Comparator compares by name, type and universe levels only; the v2 run lists no holes, so it is the run in which the definition bodies were compared by Comparator (before it, they were attested by the verbatim copy in the challenge and by the audit compile)."

## 3. The trust base

- **M3.1 The table of what is trusted.** `KIT/docs/PROTOCOL.md` lines 60 to 70, one row each: "Lean's kernel, and the Lean release it ships in"; "Comparator and lean4export"; "Mathlib's definitions"; "Mathlib's prebuilt cache"; "The challenge file and OpenAI's lakefile"; "The dependencies' build configuration"; "landrun, Landlock, systemd, the Linux kernel"; "Go and its module proxy"; "The machine and its operator". - **M3.2 The same list in the receipts.** `RECEIPT.md` line 40: "It trusts: Lean's kernel and the released Lean toolchain; Comparator and lean4export; Mathlib's definitions and its prebuilt cache; OpenAI's challenge file and lakefile (read when the kit was written, pinned by sha256); landrun, Landlock, systemd and the Linux kernel for the sandbox; this machine and whoever operated it." `RECEIPT-zeta23.md` line 311 adds NanoDa: "It trusts: Lean's kernel and the released toolchain and NanoDa; Comparator and lean4export; Mathlib's definitions and its prebuilt cache; the project's challenge files and lakefile (pinned by sha256); landrun, Landlock, systemd and the Linux kernel for the sandbox; this machine and whoever operated it."
- **M3.3 The prebuilt Mathlib cache is trusted and why that matters.** `KIT/docs/PROTOCOL.md` line 65: "By default the compiled Mathlib comes from Mathlib's own server (`lake exe cache get`), as OpenAI's instructions and Comparator's README both allow. - **M3.4 What is not trusted.** The solution side. `PINS-zeta23.env` lines 20 to 21: "Challenge.lean inlines ChallengeDeps.lean's definitions and imports only Mathlib; Solution.lean is the untrusted side." The proof files are compiled only inside the sandbox: `KIT/docs/PROTOCOL.md` lines 77 to 80: "The tree is fetched fresh; phase 5 and phase 6 both check that no build output of the challenge, the solution, or the two third-party libraries exists before the run. - **M3.5 Comparator's six stated assumptions and how the kit meets them.** `KIT/docs/PROTOCOL.md` lines 74 to 88: "1. *Challenge imports and lakefile are yours or trustworthy.*"; "2. *The solution was never compiled outside the sandbox.*"; "3. *landrun and lean4export are available.*"; "4. *landrun works and is not exploited.* Phase 3 tests it by behaviour. - **M3.6 For the add-on runs the challenge is the author's own file.** Runs 3 to 11 are judged against challenge modules generated from the author's sources (section 10), so assumption 1 holds by construction and the reader's check is to read the challenge statements. ## 5. Cold and warm runs

- **M5.1 Definitions.** `KIT/docs/PROTOCOL.md` lines 176 to 177: "A **cold** run starts from a tree in which nothing has been compiled. That is the situation Comparator's assumption 2 describes, and only a cold run can end in PASS." Lines 185 to 188: "A **warm** run (`06_run_comparator.sh --warm`) skips the rebuilding: it goes again in the tree as the failed attempt left it. It is a diagnostic ... If Comparator accepts in a warm run the verdict is PROVISIONAL, not PASS, because of what a warm run leaves open."
- **M5.2 What a warm run leaves open.** Same file, lines 188 to 195: "During the earlier attempt the proof's files were compiled inside the sandbox, which may write anywhere under `.lake`. A hostile proof could have used that to prepare the ground for the next run: a doctored compiled challenge, altered compiled dependencies, a planted program or library in a directory that `lake env` puts on the search paths, or changes to a dependency's build configuration, all of which the next run would pick up outside the sandbox. ## 11. Lessons the record documents

### L1. Mirrors must be module for module when definition bodies are compared

- **Mechanism.** `REPO/sources/qrh-mnf-addon-v3/scripts/gen_challenge.py` lines 10 to 15: "Why mirror module by module: Lean abstracts the proof terms inside a definition (such as the `Nat.AtLeastTwo` instance inside `1/2 : ℝ`) into auxiliary lemmas named `<decl>._proof_n` and reuses one already created in the same module, so a challenge with a different module structure gives some definition a different auxiliary lemma, and Comparator, which compares definition bodies (`definition_names` is empty), rejects the pair although the text is the same.  Found by the v2 pre-check on 2026-10-28."
- **The concrete instance.** `REPO/sources/qrh-mnf-addon-v2/README.md` lines 38 to 44: "For the bodies to be identical constant for constant, the challenge mirrors the sources module by module (same Mathlib imports, same `open`s, same order): Lean abstracts the proof terms inside a definition (for instance the `Nat.AtLeastTwo` instance inside the real numeral `1/2`) into auxiliary lemmas and reuses one already made in the same module, so a single-file challenge gives `LeftCriticalStrip` the auxiliary lemma of `ShiftedZeroSpectrum` and Comparator rejects the pair; the local pre-check found exactly that."
- **Restated in the final generator.** `GEN` lines 10 to 13: "Lean abstracts the proof terms inside definitions into auxiliary lemmas numbered per module, and Comparator compares definition bodies (`definition_names` is empty), so a mirror that was not laid out exactly like its source would make some definition's auxiliary lemma differ and be rejected."
- **Why it did not show in run 3.** In run 3 the definitions were holes, compared without bodies (M1.5, M1.6), and the challenge was a single file (M10.9).
- **Status of the evidence.** The rejection is described in the two READMEs and two generator docstrings; the log of the rejecting pre-check of 2026-10-28 is not among the files of the record that were searched (no file under `REPO/sources` or `NOTES` other than the kit's controls and documentation contains a Comparator mismatch message).

### L2. A claimed statement must not mention a theorem as a term

- **The rule.** `gen_challenge.py` (add-on v3) lines 15 to 17: "A second rule, found by the zeta23 add-on's pre-check the same day: no theorem statement may mention another theorem as a term, because Comparator compares a theorem reached that way in full, proof included." In a challenge every proof is `sorry`, so a theorem reached from a claimed statement cannot agree with its proved counterpart.
- **The typical case: `toFinset` of a finiteness proof.** `GEN` lines 47 to 51: declarations are omitted when their statements "use a finiteness proof as a term (`.toFinset`, which makes Comparator compare that proof)". Example of an excluded statement, `REPO/sources/qrh-zeta23-addon-v6/MNF/RH/Cube.lean` lines 585 to 586: `theorem aux_pairSum_eq_finset_sum (T : ℝ) (f : ℝ → ℝ → ℝ → ℝ) :` / `pairSum T f = ∑ ρ ∈ (zerosIn_finite 0 T).toFinset, ∑ ρ' ∈ (zerosIn_finite 0 T).toFinset,` where `zerosIn_finite` is a theorem.
- **The remedy used: take the finiteness proof as a hypothesis.** `REPO/sources/qrh-zeta23-addon/MNF/RH/Counting.lean` lines 103 to 104: `theorem Ncount_eq_sum {T₁ T₂ : ℝ} (hfin : (zerosIn T₁ T₂).Finite) :` / `Ncount T₁ T₂ = ∑ ρ ∈ hfin.toFinset, zeta_order ρ :=`. `NOTES/cube/NODE_REPORTS.md` line 71: "`pairSum_eq_sum {T : ℝ} (hfin : (zerosIn 0 T).Finite) (f)` takes the finiteness proof as a HYPOTHESIS (same convention as the tree's `Ncount_eq_sum`), so its statement contains no proof term and it needs no `aux_` prefix". The plan's rule, `NOTES/cube/CUBE_PLAN.md` lines 71 to 72: "name it `aux_pairSum_eq_finset_sum` if its statement must mention `.toFinset` of the finiteness proof (that is a proof term in a statement: keep such lemmas `aux_`)."
- **Counts defined without a proof term.** The window counts are finite sums over a set (`NOTES/cube/CUBE_PLAN.md` line 21: "`Ncount T₁ T₂ := ∑ᶠ ρ ∈ zerosIn T₁ T₂, zeta_order ρ`"), and the review of run 6 records "every count threads the finiteness lemma" (`REPO/sources/qrh-zeta23-addon/README.md` lines 68 to 69).
- **Status of the evidence.** The rule is stated in generator comments, a plan and a node report; no log of a rejection caused by it is in the record.

### L3. Constants fixed by `Classical.choose` and zeta23-internal names are kept out of claimed statements

- **The exclusion rule.** `GEN` lines 47 to 51: "declarations omitted from a mirror (and from the claim set) because their statements mention zeta23-internal objects (Zeta23.Ncount, ell1, zetaZeroConfig, Zeta23.reflect) or a constant fixed by Classical.choose (CG, meanSquareB, A₀), or use a finiteness proof as a term (`.toFinset`, which makes Comparator compare that proof); the results claimed in their place are the existential / MNF-vocabulary statements that follow them in the same file".
- **Why zeta23-internal names cannot appear: the mirror imports only Mathlib and other mirrors** (M10.3), so such a name does not exist there. Demonstrated by the failed pre-check of L5: "Unknown identifier `Zeta23.reflect`". The planning rule, `NOTES/cube/CUBE_PLAN.md` lines 8 to 12: "Statements must mention only Mathlib names and names of the `MNF.RH` namespace ... A lemma whose STATEMENT needs a zeta23-internal name (`Zeta23.reflect`, `Zeta23.zetaZeroConfig`, `Zeta23.Ncount`, `ell1`, ...) must be named `aux_…` (such lemmas are kept out of the challenge). Proofs may use anything."
- **What a `Classical.choose` constant is here.** `NOTES/reservoir/RESERVOIR_WORKFLOW_NOTES.md` line 12: "`noncomputable def Zeta23.BL.CG : ℝ := max (Classical.choose (BLClosure.zeta_approx_sharp (σ₀ := 1 / 2) one_half_pos')) 0`"; line 33: "named `CG := max C₀ 0` (a noncomputable def by Classical.choose, so that \"the same B\" is literal across the two main theorems)". The body of such a definition contains a theorem (`BLClosure.zeta_approx_sharp`) as a term, which is the situation of L2; `meanSquareB` and `A₀` are defined from `CG` (`NOTES/zeta23-tree/MNFChallengesD/ReservoirMass.lean` lines 137 and 205: `noncomputable def meanSquareB : ℝ := 951 + 4 * CG ^ 2`, `noncomputable def A₀ : ℝ := 54 + 27 / 2 * meanSquareB + 12 * Real.log 3`). The connection between the `Classical.choose` exclusion and L2 is an inference from these files; the generator comment gives the three reasons side by side and does not spell it out.
- **What is claimed instead.** Existential statements: `REPO/sources/qrh-zeta23-addon-v6/README.md` lines 39 to 42: "The 27 declarations of `ReservoirMass.lean` whose statements mention zeta23-internal names (`Zeta23.Ncount`, `ell1`, `reflect`, the `Classical.choose` constants) or a finiteness proof as a term are not in the claim set either; the existential statements that follow them in the file are." Consequence recorded in the register, `REPO/DEPOSIT_MAP.md` (row `Zeta23.BL.bohrLandau_explicit`): "with A and B explicit up to the tree's two existential constants (the approximate-formula constant at σ₀ = 1/2 and the unit-window Riemann–von Mangoldt constant)".
- **The definitions themselves stay in the mirror.** The generator drops only `theorem`/`lemma` declarations (M10.4, M10.6); `def CG` is present in the mirror (`NOTES/zeta23-tree/MNFChallengesD/ReservoirMass.lean` lines 116 to 117). See open question Q2.

### L4. How the axiom audit works

- **Two layers.** (i) Comparator's own check against `permitted_axioms` (M1.7), which is part of every accept. (ii) A separate audit compile after the run, whose output is the source of the report's statement block and axiom table.
- **The audit file.** Generated with the challenge (M10.7): one `#print axioms` and one `#check @name` line per claimed theorem.
- **How it is compiled.** Plain `lean` inside landrun against the tree Comparator built, only if the solution's compiled module exists (`z23_density_report.sh` lines 44 to 51: `if [ -f "$Z23/.lake/build/lib/lean/MNF/RH/DensityAll.olean" ]` ... else "was not compiled by the Comparator run; no audit possible").
- **What the checker requires of the output** (`z23_density_check.py` lines 129 to 150): exit code 0 ("the audit compile exited with {a.audit_rc}"); no error diagnostic ("audit error: "); no occurrence of the word sorry (`if re.search(r"\bsorry", audit): problems.append("the audit output mentions sorry")`); for each name in `theorem_names` an axiom report ("no axiom report for {name}"), exactly one ("axiom reports for {name}, expected exactly one"), with no axiom outside `ALLOWED = {"propext", "Classical.choice", "Quot.sound"}` ("{name} depends on {', '.join(extra)}"). Any problem turns an accept into `REJECTED` (lines 151 to 152).
- **Result for run 11.** `EXT/qrh-zeta23-density-v6-receipt/density-v6/audit.out` has 534 lines of the form "'MNF.RH.N0_le_Ncount' depends on axioms: [propext, Classical.choice, Quot.sound]" (first line quoted; count by grep of "depends on axioms").
- **Why the audit matters in a tree that contains `sorry`.** `Zeta23/BohrLandau.lean` keeps two sorried lemmas outside the claim set; the reports say so ("sorries outside the claim set: Zeta23/BohrLandau.lean: meanSquare_strip, rightHalfBound_of_meanSquare (not in the claim set)") and the add-on README states the role of the audit: "No claimed theorem depends on them (the audit prints every claimed theorem's axioms)" (`qrh-zeta23-addon-v6/README.md` lines 37 to 38). A dependence on a `sorry` would appear as `sorryAx` in an axiom report and be rejected by both layers.
- **Why the two sorried lemmas are still there.** Same README, lines 36 to 37: "the original file is kept unchanged with its sorries so that the receipts of v2 and v3 remain reproducible".
- **Runs 1 and 2.** Run 2 uses the project's own `scripts/PrintAxioms.lean` (`RECEIPT-zeta23.md` lines 278 to 298, 17 lines "depends on axioms: [propext, Classical.choice, Quot.sound]"). Run 1 has no separate axiom print for the theorem in the receipt; it relies on Comparator's check and on a static text scan of the 2,943 source files (`KIT/docs/PROTOCOL.md` lines 123 to 130: "found no occurrence, not even in a comment, of `sorry`, `axiom`, `native_decide`, ... A scan is not a proof of anything. It is the reason to expect no surprises, and Comparator is the check.").
- **Limit.** The audit is an ordinary compile and believes the compiled files it loads (M3.7); its statements are meaningful because Comparator's kernel replay accepted the same tree.
